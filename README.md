# AI/ML Cybersecurity Log Analysis and Alert Correlation System

An end-to-end cybersecurity analytics platform built as an AI/ML Developer Intern technical assessment project.

---

## Project Overview

This platform:
- Ingests cybersecurity event logs (CSV upload or synthetic generation)
- Detects suspicious activity using trained ML models + rule-based heuristics
- Correlates related alerts into potential security incidents
- Maps findings to ISO/IEC 27001:2022 and NIST CSF 2.0 controls
- Generates downloadable PDF security assessment reports
- Displays everything on a live React dashboard backed by a FastAPI REST API

---

## Architecture

```
Frontend (React/Vite/Tailwind) ←→ Vite Proxy ←→ FastAPI Backend
                                                    ├── ML Engine (sklearn)
                                                    ├── Detection Engine (ML + rules)
                                                    ├── Correlation Engine
                                                    ├── Compliance Mapper
                                                    ├── Report Generator (ReportLab)
                                                    └── SQLite (via SQLAlchemy)
```

**Data flow:**
1. CSV logs ingested → SQLite `security_logs` table
2. Detection engine processes logs → `alerts` table
3. Correlation engine groups alerts → `incidents` table
4. Compliance mapper maps alerts → `compliance_mappings` table
5. Report generator reads all tables → PDF

## Dataset

### Synthetic Dataset (default)
Generated by `scripts/train_model.py` and `scripts/seed_database.py`.

- **1500 normal records**: routine user activity, file access, network connections
- **500 suspicious records**: brute force, port scanning, data exfiltration, privilege escalation, malware, account lockouts

**Label assignment method**: Rule-based — a record is labelled `suspicious` if its event type matches a known attack pattern OR its `failed_login_count` / `request_count` exceeds defined thresholds.

**LIMITATION**: Synthetic labels are deterministic, not from real-world threat intelligence. The model achieves 100% metrics on this dataset because labels and features perfectly align. Real-world performance will differ significantly.

### Custom Dataset
Upload any CSV with at minimum an `event_type` column via the Logs page or `POST /api/logs/upload`.

## Running the Application

### Step 1 — Train the ML Model
```bash
cd backend
python scripts/train_model.py
```
Options:
- `--csv path/to/file.csv` — use a custom dataset
- `--normal 1500 --suspicious 500` — control synthetic counts
- `--scale` — enable feature scaling (for Logistic Regression)

### Step 2 — Seed the Database
```bash
python scripts/seed_database.py
```
This imports the synthetic dataset, runs detection, correlation, and compliance mapping.

### Step 3 — Start the Backend API
```bash
uvicorn app.main:app --reload --port 8000
```
API docs: http://localhost:8000/docs

### Step 4 — Start the Frontend
```bash
cd frontend
npm run dev
```
Dashboard: http://localhost:5173

## Model Evaluation Results (from training run)

All three models achieve 1.00 on synthetic data (expected — labels are rule-derived):

| Model | Accuracy | F1 (Susp.) | Recall | FPR |
|---|---|---|---|---|
| RandomForest | 1.0000 | 1.0000 | 1.0000 | 0.0000 |
| LogisticRegression | 1.0000 | 1.0000 | 1.0000 | 0.0000 |
| DecisionTree | 1.0000 | 1.0000 | 1.0000 | 0.0000 |

**Selected model**: RandomForest (alphabetical tiebreak, all tied at selection score 0.80)

**Selection criteria**: `0.5 × F1_suspicious + 0.3 × Recall_suspicious − 0.2 × FPR`

> **Important**: 100% metrics reflect deterministic synthetic labels. Expect significantly lower metrics on real security logs with noisy, overlapping patterns.

### False Positives vs False Negatives
- **False Positive**: A normal event flagged as suspicious. Costs analyst time.
- **False Negative**: A real attack missed by the model. Security risk.
- In security contexts, **low false negatives (high recall) are prioritised** over low false positives — missing an attack is worse than an extra alert.

## Alert Correlation

The correlation engine groups related alerts into potential incidents using:
1. **Same source IP within a 30-minute time window** — suggests the same attacker
2. **Same target asset within the same window** — focused attack on one system
3. **Attack chain patterns** — sequences like `port_scan → brute_force` are flagged as multi-stage attacks
4. **Standalone high/critical alerts** — single severe events get their own incident record

Configuration in `backend/app/correlation/engine.py` — `CORRELATION_CONFIG` dict.

**Result from synthetic dataset**: 500 alerts → 378 potential incidents

## Limitations and Future Improvements

**Current limitations:**
1. Synthetic dataset — 100% metrics are not representative of real data performance
2. SQLite — not suitable for production concurrent access; use PostgreSQL for deployment
3. No authentication — the API has no auth layer; add OAuth2/JWT for production
4. Single-node — no support for distributed log ingestion
5. Rule-based correlation — no graph-based or ML-driven correlation

**Future improvements:**
- Train on a real dataset (CICIDS2017, UNSW-NB15)
- Add BERT/transformer-based log analysis
- Implement streaming ingestion (Kafka)
- Add user authentication
- STIX/TAXII threat intelligence integration
- Automated incident response playbooks

## Interview Explanation

### Why these models?
Random Forest, Logistic Regression, and Decision Tree were chosen for their complementary properties: RF handles class imbalance and non-linear patterns well; LR provides fast, interpretable linear baselines; DT gives transparent rule extraction. All three are evaluated on the same held-out test split so comparison is fair.

### How does alert correlation work?
Alerts are grouped by shared source IP within a 30-minute sliding window. If the same IP appears in 2+ alerts within the window, they become an incident. A second pass groups by affected asset. Known multi-stage attack sequences (e.g. port scan followed by brute force from the same IP) trigger a named attack chain category.

### How are false positives handled?
The model uses `class_weight='balanced'` to compensate for class imbalance. The detection engine requires an ML confidence ≥ 0.55 before accepting an ML-only prediction. The selection criterion penalises high FPR (`−0.2 × FPR`). All detections are labelled "suspicious" (not "confirmed attack") to avoid over-alerting.

### How does the dashboard talk to the API?
The React frontend calls `fetch()` against relative paths like `/api/dashboard/summary`. Vite's dev server proxies those requests to `http://localhost:8000`. In production, configure nginx or a reverse proxy to do the same routing.
